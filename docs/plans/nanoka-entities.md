# Nanoka 后续实体实施计划

> [!IMPORTANT]
> 本文是 Nanoka 后续实体实施期间使用的临时计划，不是长期事实来源。全部实体完成后，应先将仍然有效的契约迁入对应正式规范，再删除本文及 `docs/index.md` 中的入口。

## 1. 目标

在不预先假定上游结构的前提下，为以下 Nanoka 实体逐步建立经过实际数据验证的规范、实现和测试：

- W-Engines（`weapon`）；
- Bangboos（`bangboo`）；
- Drive Discs（`equipment`）；
- Monsters（`monster`）；
- End Game 领域及 Shiyu（`shiyu`）、Boss（`boss`）、Simul（`simul`）子域。

实体范围和正式状态以 [Nanoka 数据源规范索引](../specs/nanoka/index.md) 为准。共享来源、HTTP、缓存、快照和发布契约以 [Nanoka 共享来源规范](../specs/nanoka/source.md) 为准。

## 2. 实施原则

- 先对全部后续实体做轻量调研，再确定实施顺序。
- 不创建未经上游结构验证的空实体规范。
- 每次只推进一个足够独立的实体或领域单元，完成“规范、实现、验证”闭环后再进入下一项。
- 实体特有规则保留在实体规范；只有被多个实体实际需要的机制才能提升为共享契约。
- 实际上游数据与设计不一致时，先修正规范，再使实现与规范一致。
- 本文只维护临时路线、检查清单、顺序和未决问题，不重复正式规范中的契约和实体状态。
- `docs/HISTORY.md` 是冻结的历史档案，不参与本计划，也不得用于记录实施过程或结果。

## 3. 总体阶段

### 阶段一：全实体轻量调研

对所有后续实体进行低成本结构探测，记录：

- 摘要和详情端点是否存在；
- JSON 顶层结构和最小样本；
- ID 的发现方式和排序要求；
- 支持的语言；
- 摘要与详情是一对一、一对多还是其他关系；
- 实体之间是否存在引用；
- 不同版本是否存在资源或结构差异；
- 与现有 Agents 抓取模型的主要差异；
- 对 fetch manifest、快照布局和离线验证的潜在影响。

完成条件：

- 每个实体或子域至少检查一个有效版本；
- 已记录资源发现方式和语言覆盖；
- 已识别明显的跨实体依赖；
- 已列出可能影响共享基础设施的差异；
- 信息足以确定普通实体的建议实施顺序；
- 未将未经确认的结构写成正式契约。

#### 阶段一结果（2026-07-27）

阶段一已完成。调研以正式服 `3.0` 为主要样本，并使用 `3.1.5+17516165` 和 `3.1.12+17625891` 检查版本差异。所有请求均为低频、只读的最小样本探测；本节只记录实施决策所需结论，不把抽样结果提升为正式实体契约。

所有目标实体和子域均确认存在以下资源模式：

```text
/zzz/{version}/{entity}.json
/zzz/{version}/{language}/{entity}/{id}.json
```

详情 ID 均可从对应摘要对象的顶层 key 动态发现。上游 manifest 的 `zzz.new` 只反映版本新增记录，不能作为完整资源索引。

| 实体或子域                | `3.0` 摘要数 | `3.1.12+17625891` 摘要数 | 轻量调研结论                                                                                  |
| ------------------------- | -----------: | -----------------------: | --------------------------------------------------------------------------------------------- |
| W-Engines (`weapon`)      |           93 |                       95 | 接近 Agents 的“摘要 ID → 每语言单详情”模型；详情包含升级、天赋和材料引用。                    |
| Bangboos (`bangboo`)      |           40 |                       42 | 同样是一对一详情模型，但合法详情可包含空等级、空技能参数和空图标。                            |
| Drive Discs (`equipment`) |           28 |                       30 | 结构最小且暂无明确跨实体引用；摘要已内嵌多语言内容，详情仍包含额外故事和图片字段。            |
| Monsters (`monster`)      |          288 |                      293 | 外层摘要 ID 对应单个语言详情，但详情中的 `monster_info` 可包含多个战斗单位 ID。               |
| Shiyu (`shiyu`)           |           56 |                       59 | 常驻和轮换记录的时间字段不同；阶段必须从 `zone` key 发现，不能由详情 ID 或 `stage_num` 推导。 |
| Boss (`boss`)             |           41 |                       44 | 常规详情使用顶层 `zone`；最新版本已出现使用顶层 `modes` 的真实结构分支。                      |
| Simul (`simul`)           |            3 |                        3 | 详情是 node、battle、layer、room 组成的图状结构，不适用普通阶段列表模型。                     |

语言结论：

- 各实体摘要均观察到 `zh`、`en`、`ja`、`ko` 内容；
- 每个实体或子域至少一个样本的四语言详情路径已返回有效 JSON；
- 尚未穷举证明所有 ID 的四语言覆盖完整；
- 当前正式来源配置仍只支持 `zh`、`en`，是否扩大语言范围留待共享影响评估，不因端点可访问而自动扩展契约。

已确认的依赖和结构差异：

- Shiyu、Boss 和 Simul 的遭遇数据都包含 Monster 引用；`monster_list` 外层 key 不是规范 Monster ID，嵌套记录的 `id` 才能在已检查样本中匹配 `monster.json`；
- End Game 内嵌的 Monster 数据还包含关卡特定的数值、弱点和图片，不能简化为纯外键；
- 三个 End Game 子域拥有独立摘要和详情，在传输层可以独立抓取；当前样本未发现它们彼此直接引用；
- 需要 Monster 引用闭合时，End Game 离线验证必须使用同版本 Monster 数据；
- End Game 正式建模应采用一份领域规范加 Shiyu、Boss、Simul 三份子域规范，领域规范负责共享引用和整体一致性边界；
- `equipment`、`weapon`、`bangboo` 可用于逐步验证普通多实体机制；`monster` 应在 End Game 前完成。

对共享基础设施的已识别影响：

- 当前 URL allowlist、asset kind、实体 ID 字段、summary、CLI 进度和离线验证均硬编码 `character`；
- 当前实现中的 `nanoka-fetch-manifest/v1` 实际要求恰好一个 Character 索引及其 `zh/en` 详情，不能直接登记新实体 asset kind；
- 原始字节、HTTP 元数据、条件请求、哈希、路径安全、版本锁、staging、失败保护和原子目录交换可继续作为共享基线；
- 多实体加入同一版本目录后，必须先确定 manifest 表达、单实体重跑、版本级锁和原子发布边界；
- Monster 和 End Game 需要实体内部及跨实体关系验证，不能只复用 Agents 的摘要与详情覆盖检查。

阶段一只确认端点、代表性结构和实施依赖。全量语言覆盖、全部内部引用和所有可选资源仍须在对应实体闭环中验证。

### 阶段二：共享基础设施影响评估

根据轻量调研结果确定：

- 抓取命令一次处理一个实体还是整个版本的全部实体；
- 多实体是否共用一份 `fetch-manifest.json`；
- manifest 如何表达实体类型及各实体计数；
- 多实体快照的原子发布和失败保护边界；
- 现有 `nanoka-fetch-manifest/v1` 是否足够；
- 目录、缓存、并发、进度和离线验证是否需要共享扩展；
- 如何保持现有 Agents 快照和验证行为兼容。

完成条件：

- 跨实体机制有明确归属；
- 必要的共享契约变更已写入 `source.md`；
- 实体特有差异没有被过早泛化；
- 已确认首个实体可以在稳定边界上实施。

#### 阶段二结果（2026-07-27）

阶段二已完成共享契约设计。现有 `v1` 已确认是完整 Agents 快照格式，不适合承载真正的多实体语义；多实体采用 `nanoka-fetch-manifest/v2`。长期契约统一见 [Nanoka 共享来源规范](../specs/nanoka/source.md)，Agents 的兼容对应见 [Nanoka Agents 数据规范](../specs/nanoka/agents.md)。

阶段二路线结论：

- 版本目录、单一 fetch manifest、锁、staging、验证和原子发布继续作为组合快照边界；
- 实体 adapter 作为网络更新选择和实体内部验证边界；
- 无实体参数时更新全部支持实体，定向重跑必须基于能提供全部未选实体的完整旧快照；
- 旧 v1 保持严格可读，只在成功发布中迁移为 v2；
- 当前继续支持 `zh/en`；
- Drive Discs（`equipment`）可以进入单实体标准流程。

阶段二只记录当时的设计结果。上述 v2、实体 adapter、定向重跑和分层验证随后已在 Drive Discs 闭环中实现并完成在线验收，长期契约以共享来源规范为准。

### 阶段三：确定实施顺序

优先级依据：

1. 被其他实体引用的基础实体；
2. 结构清楚且能验证共享设计的实体；
3. 普通独立实体；
4. 关系复杂或版本差异明显的实体；
5. End Game 领域和子域。

#### 阶段三结果（2026-07-27）

阶段三已完成。阶段一的结构与依赖调研足以确定实体相对顺序，阶段二进一步确认首个实体能够在已设计的多实体快照边界上实施，未发现需要调整相对顺序的新依赖。确认后的实施队列及排序依据见第 6 节。

Drive Discs 是首个实体闭环，而不是绕过共享契约的独立局部快照。其实施必须先落实 `nanoka-fetch-manifest/v2`、实体 adapter、组合 staging 和分层验证等已设计但尚未实现的共享能力，并保持现有 Agents v1 快照严格可读；首次在线验收应覆盖 Character 与 Equipment 组成的多实体组合快照。

### 阶段四：普通实体逐个闭环

阶段四按以下固定顺序执行：

```text
1. Drive Discs（equipment）：同时完成多实体共享基础设施的首次实现与组合快照验收
2. W-Engines（weapon）
3. Bangboos（bangboo）
4. Monsters（monster）
```

每个实体都必须执行第 4 节的标准流程，前一个实体完成“规范、实现、在线抓取、离线验证和独立变更单元”闭环后，才能进入下一个实体。阶段四的四个普通实体、阶段五 End Game 领域调研与建模及阶段六第 6 至第 8 项均已完成。下一步进入阶段七第 9 项综合验收。

### 阶段五：End Game 领域调研与建模

在创建 End Game 正式规范前确认：

- Shiyu、Boss 和 Simul 是否共享赛季、阶段、关卡或其他 ID；
- Boss 是否引用 Monsters 或其他普通实体；
- 是否存在版本相关的可选资源；
- 三个子域能否独立抓取、发布和验证；
- 是否必须整组抓取才能满足一致性要求；
- 应使用一份领域规范，还是领域规范加子域规范。

完成条件：

- 领域边界和子域关系已由实际数据支持；
- 正式规范的拆分方式已确定；
- 子域实施顺序及整体一致性要求已明确。

#### 阶段五结果（2026-07-27）

阶段五已完成。调研对 `3.0`、`3.1.5+17516165` 和 `3.1.12+17625891` 的全部 End Game 摘要及 `zh/en` 详情进行了低频、只读的完整结构普查，共覆盖 312 条摘要记录和 624 份详情。正式领域契约见 [End Game 领域数据规范](../specs/nanoka/end-game.md)，子域结构分别见 [Shiyu](../specs/nanoka/shiyu.md)、[Simul](../specs/nanoka/simul.md) 和 [Boss](../specs/nanoka/boss.md) 规范。

阶段五结论：

- 三个子域拥有独立摘要和详情资源，可以独立选择网络更新，但继续共用版本级锁、staging、manifest、验证和原子发布边界；
- 未发现三个子域共享的 season、stage、zone、room、node、battle 或顶层实体 ID，也未发现子域间顶层实体直接引用；
- 三个子域都引用同版本 Monster，外键只取 `monster_list` 嵌套记录的 `id`；完整样本中的 9,197 个引用全部闭合，外层 key 全部不等于嵌套 Monster ID；
- encounter 内嵌的名称、图片、弱点和关卡数值必须保留，不能缩减为纯 Monster 外键；
- Shiyu 固定使用顶层 `zone`，zone 从对象 key 发现，child 引用在单详情内闭合，`stage_num` 不唯一，时间字段存在多种合法组合；
- Simul 是 node、story event、battle、layer、room 和 record 构成的图状结构，`next_node_unlock` 与 `next_record_unlock` 使用不同目标集合，非零 `prev_node` 的命名空间仍保持 opaque；
- Boss `3.0` 使用顶层 `zone`，两个 `3.1` 版本全部使用 `modes`；alternate mode ID 不是顶层实体或独立资源，顶层和 mode `zone_type` 不保证相等；
- Boss 与 Simul 共享同版本 `boss_adjust`，并对相同类别的 buff ID 交集保持同语言记录一致，但允许一侧存在独有 buff；
- 不要求三个子域每轮同时发起网络请求；定向更新后必须在完整 staging 中执行所有适用的 Monster 和 Boss/Simul 配置 validator；
- 正式实施顺序保持为先实现跨实体 validator 基础设施，再依次闭环 Shiyu、Simul、Boss，最后执行 End Game 整体一致性验收。

阶段五只完成经过实际数据支持的规范和实施边界，不表示三个子域已加入实体注册表或完成快照验收。

### 阶段六：End Game 子域逐个闭环

先实现共享规范已定义但代码尚未具备的跨实体 validator 注册、执行和 manifest 严格验证，再按 Shiyu、Simul、Boss 顺序逐个实施子域。每个子域仍执行第 4 节标准流程；全部子域完成后增加 End Game 整体一致性验证。

### 阶段七：全实体综合验证与计划清理

- 对完整版本快照运行在线抓取和离线验证；
- 确认所有实体的资源覆盖、计数和引用关系；
- 确认失败保护、缓存复用、原子发布和版本锁在完整范围内成立；
- 将长期有效规则迁移到 `source.md` 或对应实体规范；
- 在规范索引中更新最终状态；
- 确认本文不再包含唯一信息；
- 删除本文；
- 删除 `docs/index.md` 中的临时计划入口。

## 4. 单实体标准流程

每个实体按以下顺序完成：

1. **调研上游**：获取真实样本，确认端点、资源关系、语言、ID 和版本差异。
2. **编写规范**：定义目标、非目标、端点、发现规则、最低结构、一致性、布局、manifest 扩展、测试和验收标准。
3. **评审共享影响**：确认是否可以复用现有机制，是否需要共享契约变更或 manifest schema 升级。
4. **实现抓取**：完成资源发现、最低结构校验、路径策略、原始字节保存、清单记录和进度事件。
5. **实现离线验证**：校验文件、哈希、计数、资源覆盖及实体特有关系。
6. **补齐自动化测试**：使用 mock fetch、临时目录和最小 fixture 覆盖成功及失败路径。
7. **执行在线抓取**：选择真实版本，检查目录、资源数量、原始 JSON、清单和终端进度。
8. **验证缓存与失败保护**：重复抓取以确认条件请求或缓存复用，并确认失败不会替换完整快照。
9. **执行离线验收**：运行 verify，并在测试副本中验证缺失、篡改和关系错误能够被发现。
10. **修正规范与实现**：实际数据暴露差异时同步修正，保持规范和实现一致。
11. **更新正式状态**：将实体规范和规范索引更新为经实际验证的状态。
12. **完成独立变更单元**：完成适合独立评审和回滚的提交或 PR，再进入下一实体。

## 6. 实施队列

阶段一调研与阶段二共享基础设施影响评估后确认的实施队列为：

```text
阶段四：普通实体逐个闭环
  1. Drive Discs（equipment）
  2. W-Engines（weapon）
  3. Bangboos（bangboo）
  4. Monsters（monster）

阶段五：End Game 领域调研与建模（已完成）
  5. 完成三版本全量调研，确认领域共享边界并建立领域及三份子域规范

阶段六：End Game 子域逐个闭环
  6. 实现跨实体 validator 基础设施并闭环 Shiyu（shiyu）（已完成）
  7. Simul（simul）（已完成）
  8. Boss（boss）（已完成）

阶段七：全实体综合验证与计划清理
  9. 执行 End Game 整体引用验证及完整版本快照综合验收
 10. 迁移剩余长期契约，更新正式状态并删除本计划
```

以上是阶段三确认的完整后续执行顺序，而不只是实体优先级列表。各阶段和步骤按编号依次推进；除非实际数据暴露足以改变依赖关系的新证据，否则不并行跨越阶段，也不跳过前置闭环。

排序依据：

- Drive Discs 数量少、详情结构最小且暂无明确跨实体引用，适合作为首个实体验证多实体 manifest、布局和离线覆盖机制；
- W-Engines 与 Agents 的摘要和详情模型最接近，可在基础机制稳定后验证较大的嵌套详情；
- Bangboos 需要确保最低结构不会错误拒绝合法的空等级、空技能参数和空图标；
- Monsters 数量和详情规模最大，并包含外层实体与内部战斗单位的多层 ID，应在普通机制稳定后独立闭环；
- Monsters 是三个 End Game 子域共同引用的基础实体，必须先于 End Game 子域；
- Shiyu 的模型相对直接；Simul 是独立的图状结构；Boss 已确认存在 `zone` 与 `modes` 多形态，实施风险最高；
- End Game 全部子域完成后，再执行同版本 Monster 引用和领域整体一致性验证。

此队列是当前确定的实施路线，阶段四的四个普通实体顺序同时在对应阶段中明确。实体的正式完成状态仍只维护在规范索引中。若后续全量样本暴露新的依赖或结构分支，应先在本文记录证据、影响和调整后的完整队列，再改变实施顺序。
