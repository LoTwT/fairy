# 统一效果规则模型

状态：正式类型已迁入 `@randomplay/effects` 包（[types.ts](../../../packages/effects/src/types.ts)）并随包发布；运行时校验（`parseEffectRuleSet`）、`prepareEffects`、状态导入、外部实例同步、给定状态求值与事件推进（`advanceEffects`，含触发、激活阶段修改、时钟、叠层、冷却与稳定请求身份）均已实现，满足完整 `EffectEngine` 接口；验收矩阵见[执行契约](execution.md#求值器实现时的验收矩阵)。

代理人、驱动盘、音擎共用一套规则：**满足条件，提供效果，或修改已有的效果。** 记录数量由实际机制决定。耀嘉音的核心攻击力增益与 2 影强化分别保存，求值时先修改核心参数，再计算一次核心增益。

沿用[来源数据整合规范](../data/integration.md)的职责划分：

```text
integrated 来源资料 → definitions 效果定义
                           ↓
                集成层结合配置与运行状态
                           ↓
                     core 计算输入
```

- `integrated` 保留来源资料；`definitions` 维护经核对的计算语义及来源引用。职责名称不额外承诺新的 npm 包或公开导出。
- 集成层绑定规则持有者，维护或接收有效实例，判断适用性、求值并组装输入。相同输入产生相同结果，不改写定义或调用方对象。
- core 的计算与校验继续由[现有契约](../core/index.md)维护。效果身份、条件、事件、来源追踪与收益分析留在 core 之外。
- 定义证据不足时，可以用显式给定的有效实例验证数值；自动生成实例则必须先确认触发、计时和叠层条款。

正式类型随 `@randomplay/effects` 发布；本模型不修改来源数据或 core 的公开接口。

## 定义、绑定、实例

| 数据             | 保存内容                                         | 例子                                   |
| ---------------- | ------------------------------------------------ | -------------------------------------- |
| `EffectRule`     | 静态条件、参数、表达式、操作与生命周期           | 耀嘉音核心转化公式                     |
| `SourceBinding`  | 来源身份、持有者、适用性、培养或装备配置         | 本次耀嘉音为 2 影、核心等级 7          |
| `EffectInstance` | 当前有效层、受益对象、触发上下文、时钟与快照引用 | 某次入场使耀嘉音与队友获得有效核心增益 |

效果定义不会因为当前档位改变而换 ID。两名角色各装备同名音擎时，使用同一定义、不同来源绑定和运行实例。每层保留自己的触发者与快照，不能用最后一次触发替换所有旧层的上下文。

`holder`、`triggerActor`、`beneficiary` 分别表示持有者、触发主体和当前受益者；命中另有 `hitActor`、`hitTarget`。召唤物拥有独立运行时 ID 与所有者。由这些实际身份建立分组和依赖，不能把所有同名属性或同种召唤物当成同一对象。

`StateDefinition` 定义可被配置修改的状态参数。状态的实际进入、退出与召唤物行为由调用方提供 `WorldObservation`；引擎把解析后的参数交给状态维护方，不自行模拟尚无依据的游戏行为。

## 三种规则

`EffectRule` 按根字段 `kind` 区分，类型排除相互矛盾的字段：

| 类型           | 作用                              | 例子                                                  |
| -------------- | --------------------------------- | ----------------------------------------------------- |
| `contribution` | 为属性、Factor 或匹配命中提供数值 | 攻击力增益、团队增伤、震音倍率 ×2                     |
| `instant`      | 接受触发后输出一次资源或动作请求  | 入场回复能量、追加 1 道震音和 3 枚音簇                |
| `modification` | 在明确阶段修改指定贡献或状态参数  | 2 影提高核心系数与上限；丽娜 1 影放大范围内的核心结果 |

三者均有来源、配置条件和参数。贡献规则使用 `activation`、目标选择器、`scope`、`when` 与贡献操作；瞬时规则使用 `trigger`、目标选择器和一次性操作；修改规则使用目标 ID、阶段及修改列表。完整字段只维护在类型附件中。

### 贡献的激活方式

| 激活方式     | 有效性的来源                                               |
| ------------ | ---------------------------------------------------------- |
| `continuous` | 来源适用、配置及当前贡献条件满足；不需要伪造触发事件       |
| `supplied`   | 调用方明确提供有效实例，适用于已知状态的计算               |
| `triggered`  | 引擎根据已确认的触发规则维护实例，生命周期为限时或状态绑定 |

触发条件只控制是否新建或刷新。持续生效条件、结束条件是另外的语义，不能从“在某状态下触发”推导出“退出该状态就移除增益”。本版不定义没有样例依据的暂停行为。

### 贡献的落点

- `stat-adjustment`：通用属性区分初始/最终百分比、固定值；暴击率、暴伤、穿透率等直接属性用 `direct`，配合 `scope: hit` 表达单次命中的属性调整。
- `factor-contribution`：向已登记 Factor 通道提供贡献，如 `0.1` 增伤，不把最终倍率 `1.1` 当作加数。
- `hit-adjustment`：对匹配命中的倍率进行 `scale`。

实体作用域和命中作用域分开。6 影震音的暴击率提高不会写回角色通用面板。一次性回能和追加攻击也不会作为持续贡献在每次查询时重新输出。各落点与 core 参数的唯一映射维护在[输出适配](execution.md#输出适配)。

## 基础效果如何被强化

耀嘉音核心 7 级的基础规则：

```text
参数：ratio = 0.35，cap = 1200
结果：min(持有者初始攻击力 × ratio, cap)
```

2 影另外保存一条修改规则：

```text
条件：mindscapeRank >= 2
目标：同一持有者的核心攻击力转化
修改：ratio 加 0.19，cap 加 400
```

因此 0—1 影仍用原参数；2—6 影先得到 `ratio = 0.54、cap = 1600`，再执行同一公式。基础规则没有被跳过，也没有额外叠加一份完整的强化核心，更不需要用负数效果抵消旧核心。

核心等级和影画分别处理：等级表先选择对应系数，影画修改再作用于所选值。2 影新增的免费追加动作是另一项独立机制，需要另外的瞬时规则，不能塞进这条参数修改中。

### 修改参数与修改结果

| 修改位置     | 计算方式                                     | 对应实例                                |
| ------------ | -------------------------------------------- | --------------------------------------- |
| 参数         | 修改后再执行基础表达式，包括表达式内部的封顶 | 耀嘉音 2 影改变转化比例和上限           |
| 输出结果     | 基础表达式完成后，对本层结果加算或缩放       | 丽娜 1 影范围内把已封顶的核心增益乘 1.3 |
| 生命周期参数 | 在配置解析或被接受的触发时确定新建/刷新时长  | 合成条件时长夹具                        |
| 外部状态参数 | 向状态维护方提供修改后的参数                 | 召唤物逗留时间延长的建模方式            |

同一阶段、同一字段按 `set → add → scale` 处理；不同有效 `set` 冲突必须报错。按受益者或命中判断的修改只作用于局部结果，不能改共享定义。配置阶段与战斗阶段允许的修改范围见[修改的解析](execution.md#修改的解析)。

比较升级收益时，固定其他原始输入，分别计算修改前后结果再相减。以初始攻击力 3000 为例，核心从 1050 变为 1600，提升 550；不能简单把 `0.19 × 3000` 当作已考虑封顶的提升。此例只比较核心强化，不等于 0 影与 2 影全部战斗收益。

## 条件、单位与属性依赖

条件和表达式是封闭的类型联合，不执行字符串代码或任意对象路径。条件按配置、触发、贡献阶段限定可读事实：触发时可以同时读取事件和事件前状态；贡献阶段可以按目标及命中判断。事实缺失与条件为假是不同结果。

数值使用明确单位：攻击力点数、能量点数、秒、米、计数、比例与乘数。比例用小数；`add 0.19 ratio` 是加 19 个百分点，`scale 1.19 multiplier` 是放大到 1.19 倍。等级表缺档位或单位不匹配都不能默认补值。

属性读取同时指定实体、属性阶段和时间：

- `initial` / `current` 表示属性公式阶段；初始属性不等于战斗开始时的快照。
- `before-event`、`activation`、`evaluation`、`action-start` 指不同读取时点。旧快照缺失不能拿最新属性代替。
- 读取与写入按实际实体、属性阶段、时点及命中作用域建图。属性聚合节点先处理有效贡献与唯一性，再向下游提供结果。
- 真正的循环依赖应报告完整路径，不能擅自改成触发快照来消除报错。

具体事件需要明确关联。例如耀嘉音核心要把同次入场、耀嘉音的追加攻击及其实际能量消耗关联起来，两个独立布尔开关不能表达这个条件。

## 状态推进与数值查询

完整契约包含初始化、外部实例同步、事件推进和查询接口；先实现给定状态的求值，再接入事件推进：

```text
prepareEffects：定义 + 来源配置 → 有效定义与状态参数
supplyEffectState：显式有效层 + 快照 → 运行状态
synchronizeSuppliedInstances：旧状态 + 外部实例替换 → 保留其他状态的新状态
advanceEffects：旧状态 + 单个事件 + 世界观察 → 新状态 + 一次性请求
evaluateEffects：状态 + 世界观察 + 查询 → 贡献与计算输入
```

持续时间、叠层、冷却和唯一性各有独立职责：

| 规则     | 决定的问题                                       |
| -------- | ------------------------------------------------ |
| 生命周期 | 何时结束，重触发时刷新还是延长，共用还是逐层计时 |
| 叠层     | 哪些触发属于同一组，每组最多几层，满层如何处理   |
| 冷却     | 某组触发何时可以再次被接受                       |
| 唯一性   | 多个来源都有效时，哪些来源的贡献进入计算         |

满层不自动等于不刷新，未被唯一性选中的来源也不自动清除状态。多个输出共享一次触发时，在同一个旧状态上判断冷却后原子提交。重复查询不会重复执行瞬时效果。

外部实例同步只替换明确指定的效果与来源绑定，保留引擎维护的层、冷却和已有历史。状态重新进入时，以新的激活身份建立叠层组；本事件的条件与激活快照仍读取事件前状态。

唯一性在本次计算的实际消费位置上判断：通用增伤与命中增伤同时参与同一命中时，先统一到该命中的地址再选择，不因定义作用域不同而重复相加。

计时公式、事件顺序、快照绑定、来源选择及错误行为都由[执行契约](execution.md)规定。尚未证实的游戏机制只保留在[实例页的证据缺口](examples.md#尚需补充的游戏证据)，不在代码里偷偷选默认答案。

## 类型与实施验收边界

包内正式类型已经覆盖规则、条件、表达式、单位、修改、配置绑定、状态/事件/快照、输出、错误及五个接口；合法实例与类型反例可独立编译，且由 `parseEffectRuleSet` 在运行时复验。跨字段、目标引用、实际上下文和数值依赖由运行时校验承担，TypeScript 通过不等于游戏机制已经验证。

实施范围以[实施阶段](execution.md#实施阶段)为准：配置修改在准备阶段折叠，数值依赖按需递归求值；第一阶段交付给定状态的计算与外部实例同步，第二阶段增加自动事件推进。层数上限、受益对象和生效条件的专用修改字段尚无真实用例，暂未纳入当前修改类型，扩展要求见同节。

可执行验收预期见[校验与验收](execution.md#校验与验收)。耀嘉音须覆盖不同核心等级、全部影画及封顶前后，不能只用核心 7 级、攻击力 3000 的单点验收。新增事实或操作时同步扩展类型、执行语义、core 落点和验收样例；不能以任意字符串、脚本或未知字段绕过本规范。
