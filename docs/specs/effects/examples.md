# 效果规则实例与核对记录

本文配套[统一效果规则模型](index.md)。表格描述规则记录和给定状态下的求值；不是已经发布的机器规则集，也不代表这些来源的全部条款已经覆盖。对应的 [TypeScript 实例](contract-examples.ts) 用于验证[类型与执行契约](execution.md)，其中的合成时序前提不能作为游戏依据。

标注分为：**来源事实**（文本直接支持）、**设计约定**（本模型的处理方式）、**待确认机制**（尚缺行为证据）。待确认机制不会以注释伴随一个默认值进入可执行规则：对应事件推导或依赖它的场景暂不支持。数值验证可以使用明确给定的有效实例、读取值与作用对象，不冒充已经验证触发过程。

## 耀嘉音：核心基础效果与 2 影修改

### 规则记录

| 字段       | 基础效果                                        | 2 影修改                                                         |
| ---------- | ----------------------------------------------- | ---------------------------------------------------------------- |
| `effectId` | `agent:1311:core:attack-conversion`             | `agent:1311:mindscape-2:core-enhancement`                        |
| 来源位置   | 核心被动等级条款                                | 影画 2 条款的核心强化部分                                        |
| 配置       | 绑定耀嘉音与实际核心等级                        | 同一持有者影画至少 2                                             |
| 操作       | `stat-adjustment`，攻击力，`final-fixed`        | `kind: modification`，精确引用左侧效果                           |
| 参数       | `ratio` 按核心等级取值；`cap = 1200` 攻击力点数 | `parameters.ratio add 0.19`；`parameters.cap add 400` 攻击力点数 |
| 表达式     | `minimum(ratio × 持有者初始攻击力, cap)`        | 保留基础表达式，先应用参数修改                                   |
| 受益对象   | 持有者与本次入场队友                            | 继承基础效果                                                     |

来源给出的核心等级 1—7 系数为 `0.22、0.24、0.26、0.28、0.30、0.32、0.35`。用实际档位作键选参，不使用没有定义起点的数组索引。

来源事实：在咏叹华彩状态下，其他队员通过快速支援、连携技、招架支援或回避支援入场，且耀嘉音消耗能量追加震音攻击时触发；持续 20 秒，重复触发延长，最多 30 秒。入场者、支援者与能量消耗必须属于同一次关联过程，触发者必须是持有者的队友。

咏叹华彩在该句中限定触发过程，没有据此额外添加退出状态时移除增益的规则。延长的具体基准、受益者之间的计时关系尚待核实，因此本例的事件推导部分尚不能作为完整运行规则导入；下表只验证已给定有效增益时的数值。

### 数值验收

固定核心等级 7、相同初始攻击力 `A`，基础为 `min(0.35A, 1200)`，2 影强化为 `min(0.54A, 1600)`。这不是所有 0 影与 2 影效果的总差值。

| A             | 基础核心增益 | 强化后核心增益 | 差值 |
| ------------- | ------------ | -------------- | ---- |
| 2000          | 700          | 1080           | 380  |
| 3000          | 1050         | 1600           | 550  |
| `1200 / 0.35` | 1200         | 1600           | 400  |
| 4000          | 1200         | 1600           | 400  |

边界使用精确表达式，不把 `3428.57` 当作恰好封顶的精确数。差值在 `A = 1600 / 0.54` 时达到约 `562.962963`，之后回落至 400；显示时才舍入。

实现验收使用 [contract-examples.ts](contract-examples.ts) 的 `astraCoreNumericCases`：包含核心等级 1—7、零攻击力、两个封顶点及其前后，并对每项遍历 0—6 影。固定有效核心层的内容及其他输入，每种配置分别准备并导入新会话；0—1 影匹配基础值，2—6 影匹配强化值。小数结果允许 `1e-9` 攻击力点数的比较误差，计算过程中不做显示舍入。单测攻击力 3000 无法检出“2 影固定返回 1600”或部分错误系数。

### 2 影、6 影的其他条款如何归类

2 影还新增一组追加动作：符合入场与状态条件时追加 1 道震音和 3 枚音簇，3 秒内最多一次。这是一条单独的 `action-request`，与核心参数修改分开；免费追加动作不能自动满足核心所需的能量消耗事实。

6 影至少拆为下列记录。动作语义标识是本模型登记的身份，不声称直接等于 Nanoka 的技能 ID；动作适配未核实时不导入生产规则。

| 记录                               | 条件与作用范围                                               | 操作                                                               |
| ---------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------ |
| 震音/音簇倍率强化                  | 命中主体为持有者；属于咏叹华彩状态下释放或追加释放的对应动作 | `hit-adjustment`：该命中倍率 `scale 2`                             |
| 震音/音簇暴击率强化                | 与上一行同范围                                               | `scope: hit`，`stat-adjustment / criticalRate / direct`，值 `0.80` |
| 自动追加蓄力完成的《随想曲》第三段 | 持有者触发精准支援                                           | `action-request`；这项触发有 10 秒频率限制                         |
| 上一追加招式的暴击率强化           | 匹配上述动作请求的来源及其后续命中                           | `scope: hit`，`stat-adjustment / criticalRate / direct`，值 `0.80` |

10 秒限制放在追加动作的触发记录上，不能放在暴击率贡献上形成“每 10 秒才享受一次暴击率”的另一种效果。动作来源需保留，不能仅凭“第三段”把任意普通攻击第三段都当成这次追加动作。

状态限定对应释放动作的上下文；命中延迟发生时需保留所需的释放时状态，而不是只读命中时的最新状态。具体动作标识、额外第三段与其他第三段的覆盖关系、计时起点列入证据缺口。

## 丽娜：整体强化、召唤物与局部范围

### 规则记录

| 记录                                      | 条件或目标                                               | 操作                                                     |
| ----------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------- |
| `agent:1211:core:penetration-conversion`  | 持有者指派自己的杜苏拉或安娜塔莎攻击；受益者为其他队友   | `stat-adjustment`，直接穿透率：`min(0.25P + flat, 0.30)` |
| `agent:1211:mindscape-1:core-enhancement` | 影画至少 1；受益者距离持有者的任一相关召唤物不超过 10 米 | 修改上述结果：`value scale 1.3`                          |
| `agent:1211:mindscape-1:summon-linger`    | 影画至少 1；相关召唤物被指派并攻击后                     | 修改召唤物返回前逗留时间参数：`add 5.5` 秒               |

`P` 是供本次读取的丽娜自身穿透率，`flat` 按核心等级 1—7 取 `0.06、0.075、0.09、0.102、0.108、0.114、0.12`。两只召唤物均返回后基础增益结束，这是明确的结束条件。

距离判断绑定属于该丽娜实例的杜苏拉、安娜塔莎，不能与其他持有者的同类召唤物混用。“任一只满足”与“最近距离不超过 10 米”在同一候选集合和距离度量下等价，不是两个待选择的算法。候选集合为空时条件不成立；缺少候选位置则是缺少事实，不能当成不在范围内。

这里只修改范围内受益者的计算结果，范围外仍取基础增益。读自身、写队友按实际实体建立依赖，不因属性名称相同产生假环。

### 数值验收

固定核心等级 7，且基础增益实例有效：

| P    | 基础 | 1 影、范围内 | 1 影、范围外 |
| ---- | ---- | ------------ | ------------ |
| 0.40 | 0.22 | 0.286        | 0.22         |
| 0.72 | 0.30 | 0.39         | 0.30         |

强化在基础表达式封顶之后执行，所以 30% 的基础上限可产生 39% 的最终增益，不是在乘完后再次裁剪到 30%。

5.5 秒改变的是召唤物行为。状态跟踪若由调用方提供，调用方必须使用经确认的返回时序；求值器不能一边接受未改变的返回事件，一边声称单独修改 `lingerSeconds` 已延长了实际增益。实时读取或触发快照、基础逗留及返回时序均需补证；上述数值表不依赖这些选择。

## 啄木鸟电音：独立效果与独立招式计时

| 记录                                 | 配置/触发                                                       | 数值与分组                                                   |
| ------------------------------------ | --------------------------------------------------------------- | ------------------------------------------------------------ |
| `disc:31000:two-piece:critical-rate` | 该持有者装备该套装至少 2 件                                     | 持续直接暴击率 `add 0.08`，无需触发事件                      |
| `disc:31000:four-piece:attack`       | 至少 4 件；持有者自己的普通攻击、闪避反击或强化特殊技命中并暴击 | 每个有效层攻击力提高 9%，持续 6 秒；按持有者和招式组分别计时 |

四件套时两条都存在。触发必须包含命中主体是持有者，队友或敌人的暴击不触发。不同招式的计时独立；某组达到层数上限后，是否刷新时间要按该组的重触发策略处理。

来源支持三类招式分别提供一层及分别计时；具体动作如何归类、同类重复触发的处理需要进一步核实。本例不把“共有三个名称”直接提升为已实测的所有层数与刷新行为。

数值示例明确假设攻击力贡献进入最终百分比阶段，且调用方已提供 0、1、3 个有效层；初始攻击力为 2000：

| 有效层数 | 最终百分比贡献 | 最终攻击力 |
| -------- | -------------- | ---------- |
| 0        | 0              | 2000       |
| 1        | 0.09           | 2180       |
| 3        | 0.27           | 2540       |

上表验证所选阶段下的表达式，不充当该阶段或三层触发过程的游戏证据。判别属性阶段的实测应使用基础攻击力与初始攻击力不同的样本，避免两个模型给出相同结果而无法区分。

## 玲珑妆匣：精炼选参、一次性回能与团队增伤

| 记录                                    | 配置与触发                                                     | 操作与状态                                                                 |
| --------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `w-engine:14131:energy-on-entry`        | 装备适用性满足；持有者队伍中任一角色通过指定支援或连携方式入场 | 为持有者生成一次回能请求；5 秒内最多一次                                   |
| `w-engine:14131:damage-on-energy-spend` | 装备适用性满足；持有者达到条款的 25 点能量消耗条件             | 全队增伤，每层取精炼参数，最多 2 层、20 秒，重触发刷新；该增伤条款全队唯一 |

适用性由来源绑定先行确认，不能仅因为选了精炼等级就启用不适用装备的被动。入场事件可以由持有者本人或队友发起，不包含敌方或其他队伍。

| 精炼 | 每次基础回能 | 每层增伤 | 两层增伤 |
| ---- | ------------ | -------- | -------- |
| 1    | 5            | 0.10     | 0.20     |
| 2    | 5.5          | 0.115    | 0.23     |
| 3    | 6            | 0.13     | 0.26     |
| 4    | 6.5          | 0.145    | 0.29     |
| 5    | 7            | 0.16     | 0.32     |

精炼选择一档参数，不累加 1 至当前精炼的效果。10%—16% 是**伤害加成**，不是攻击力加成，没有“该攻击力加成属于初始还是最终阶段”的待确认问题。

回能是事件结果：持续查询同一状态不会再次回能。其能量获得效率适用性需单独确认；数值表只给基础回复量，不把所有回能都默认设成可被效率放大。

同名装备的来源绑定、层数、计时及 5 秒冷却分别记录。增伤唯一性按同名效果组、受益对象和增伤输出地址处理，不能去掉其他队友本来应得到的贡献。不同来源同时生效时选择哪一份、层数与强度如何参与选择尚未证实；不能默认为高精炼优先，也不能自行规定一个游戏不存在的优先级。

## ZZZ-HP 的参考边界

核对版本固定为 `0df40c5bc38f8da7ed0f9eed6be87fb8155b8357`。[转化实现](https://github.com/Nie7bai/ZZZ-HP/blob/0df40c5bc38f8da7ed0f9eed6be87fb8155b8357/zzz-hp/src/utils/buffEffect.ts#L447-L503)先计算转化值，再统一使用 `Math.min(amount, cap)`。

[耀嘉音 2 影记录](https://github.com/Nie7bai/ZZZ-HP/blob/0df40c5bc38f8da7ed0f9eed6be87fb8155b8357/zzz-hp-backend/scripts/data/zzz-hp-calculator-buffs.json#L69713)在基础 `35% / 1200` 之外加入 `54% / 1600` 与 `-35% / 1200`；后两者的默认读取值分别是 2963 与 3428.56，基础默认值也是 3428.56。

即使把三处读取值统一为 4000，按源码算法仍有：

```text
min(4000 × 0.35, 1200)
  + min(4000 × -0.35, 1200)
  + min(4000 × 0.54, 1600)
= 1200 - 1400 + 1600
= 1400
```

负数项没有形成所需的 `-min(4000 × 0.35, 1200)`，所以结果不同于直接使用新核心得到的 1600。默认读取值不一致是另一项风险，不能把两者混成同一个问题。这里是源码与算术核对，不是完整应用执行结果。

可参考其固定增益、叠层、转化、适用目标等拆分方式；不能把空记录、未编码时序或同输入结果直接当作游戏机制的正确性依据。新模型以真实条款、已确认的机制和 core 契约分别验收。
